# 10 — التقييم المعماري (Architecture Assessment)

> **الدور:** المهندس المعماري المسؤول عن Dueli
> **تاريخ التقييم:** 2026-09-05
> **الفرع المفحوص:** `main` @ `57016c9`
> **طريقة العمل:** فحص الكود المصدري مباشرةً + قياسات آلية. كل رقم في هذه الوثيقة قابل لإعادة التوليد بأمر مذكور بجانبه.

---

## 0. ملخص تنفيذي

Dueli **ليس مشروعاً يحتاج إعادة بناء**. النواة المعمارية سليمة: طبقات MVC واضحة، `BaseModel`/`BaseController` مطبّقان، i18n مركزي، ترحيلات متسلسلة، وTypeScript يمرّ بـ`strict: true` بصفر أخطاء.

المشكلة ليست في الميزات — **الميزات كثيرة**. المشكلة في أن المشروع **لا يملك آلية تُثبت أنه يعمل**. لا يوجد اختبار آلي واحد مقابل 43,762 سطراً و191 مساراً. كل ادعاء "✅ مكتملة ومختبرة" في `PLAN-STATUS.md` يستند إلى فحص يدوي غير قابل لإعادة التشغيل. هذا يعني أن أي تعديل مستقبلي هو مقامرة.

**الحكم المعماري:** المشروع في حالة **"يعمل ولا يمكن الدفاع عنه"** (Works but Undefendable). الانتقال إلى الإنتاج يتطلب مرحلة تثبيت (Stabilization) لا مرحلة توسّع.

## 1. ما هو سليم فعلاً (لا تلمسه)

قبل النقد، تثبيت ما نجح — لأن إعادة هندسته خسارة صافية:

1. **فصل الطبقات موجود ومُوثّق.** `docs/01-ARCHITECTURE-RULES.md` + `AGENTS.md` يفرضان MVC، وهذا نادر في مشاريع بهذا الحجم.
2. **`BaseModel` / `BaseController`** يوفران CRUD واستجابات موحّدة — أساس صحيح للتوسّع.
3. **TypeScript `strict` يمرّ بصفر أخطاء.** هذه إشارة انضباط حقيقية.
4. **i18n مركزي** مع دليل واضح (`docs/06-I18N-GUIDE.md`) وإضافة اللغة في 3 خطوات.
5. **الترحيلات متسلسلة وقابلة للتطبيق من صفر** — لا تعديل على ترحيلات قديمة.
6. **اختيار المكدّس (Cloudflare Pages + Hono + D1)** مناسب للحالة: تكلفة منخفضة، حضور عالمي، زمن استجابة منخفض.
7. **`WORKLOG.md` + `PLAN-STATUS.md`** ثقافة تتبّع موجودة — تحتاج تصحيح معيار "مكتمل" فقط، لا إلغاء.

## 2. المخاطر الحرجة (P0) — مؤكَّدة بالكود

كل بند أدناه فُحص في الملف والسطر. لا بند هنا مبني على استنتاج.

### P0-1 🔴 مسار إكمال التبرع يسمح بتزوير المال

**الملف:** `src/modules/api/donations/routes.ts:148`

```ts
donationsRoutes.post('/:id/complete', async (c) => {
    const donationId = parseInt(c.req.param('id'));
    const { transaction_id } = body;          // ← يأتي من العميل
    const donation = await donationModel.markCompleted(donationId, transaction_id);
```

**التحليل:** المسار **بلا أي مصادقة** (مؤكَّد: `ad-blocks/routes.ts` لا يحتوي `use(authMiddleware)`، و`main.ts` لا يطبّق auth عالمياً). أي شخص يرسل `POST /api/donations/5/complete` بجسم `{"transaction_id":"x"}` يُعلِّم تبرعاً كمكتمل دون دفع فلس واحد.

الأخطر: webhook الصحيح **موجود بالفعل** في السطر 189 مع تحقق HMAC من Stripe. أي أن المسار المكشوف هو **بقايا** كوّنت باباً خلفياً حول الحماية القائمة.

**التوجيه:** احذف المسار كاملاً. لا تُصلحه. إكمال الدفع حدث يملكه مزود الدفع فقط.

### P0-2 🔴 الرصيد المسحوب يُخصم مرتين منطقياً — خلل محاسبي

**الملف:** `src/models/WithdrawalRequestModel.ts:129`

```ts
// عند طلب السحب:
UPDATE user_earnings SET available = available - ?, withdrawn = withdrawn + ? ...
```

**التحليل:** `withdrawn` تُزاد **لحظة الطلب**، قبل صرف أي مال. ثم في `approve()` (السطر 155) لا يحدث أي تعديل مالي — فقط تغيير حالة. النتيجة:

- طلب سحب **معلّق** يُحتسب كـ"مسحوب" في التقارير.
- `reject()` و`cancelByUser()` يعكسان بـ`withdrawn = withdrawn - ?` — أي أن `withdrawn` ليس حقلاً تراكمياً بل عدّاداً متذبذباً.
- **لا يوجد حقل يمثّل "محجوز/قيد المعالجة"** رغم وجود `on_hold` في المخطط (`migrations/0001:277`) — الحقل موجود ولا يُستخدم.

**أخطر من ذلك:** لا وجود لأي معاملة ذرّية. D1 يدعم `batch()` لكن الكود ينفّذ خطوتين منفصلتين مع "rollback" يدوي في `catch`. إذا مات الـWorker بين الخطوتين، خُصم المال ولا يوجد طلب سحب. **مال يتلاشى.**

**التوجيه:**
1. استخدم `on_hold` لطلبات السحب المعلّقة. `withdrawn` يزداد **فقط** عند `approve()`.
2. المعادلة الحاكمة الواجب فرضها كاختبار: `total == available + pending + on_hold + withdrawn`.
3. كل تحويل مالي عبر `db.batch([...])` — لا rollback يدوي.
4. `CHECK (available >= 0 AND on_hold >= 0)` على مستوى المخطط.

> هذا البند **لم يُذكر في التخطيط السابق**، وهو من أخطر ما في المشروع لأنه يفقد المال بصمت دون رسالة خطأ.

### P0-3 🔴 مفاتيح رفع الفيديو تُولَّد بـ`Math.random()`

**الملفات:**
- `src/modules/api/chunks/routes.ts:18` — مفتاح رفع
- `src/middleware/security.ts:265` — **رمز CSRF**

```ts
key += chars.charAt(Math.floor(Math.random() * chars.length));
```

**التحليل:** `Math.random()` ليس مولّداً آمناً تعمّية. الأخطر أن الاستخدام الثاني هو **توليد رمز CSRF** — أي أن حماية CSRF نفسها قابلة للتنبؤ، فتصبح حمايةً شكلية.

**التوجيه:** استبدل الاثنين بـ`crypto.getRandomValues()` (متوفّر أصلاً في Workers). أضف قاعدة lint تمنع `Math.random` في `src/middleware`, `src/lib`, `src/modules/api`.

### P0-4 🔴 CORS مفتوح للعالم

**الملف:** `src/main.ts:71`

```ts
app.use('/api/*', cors());     // ← بلا origin
```

**التحليل:** `cors()` بلا إعدادات في Hono يعني `Access-Control-Allow-Origin: *`. مع كون المصادقة تعتمد `Authorization: Bearer` من `localStorage`، فأي موقع خارجي يستطيع استدعاء الـAPI نيابةً عن المستخدم إذا حصل على الرمز.

هذا يُبطل عملياً أثر `csrfProtection()` في السطر 83.

**التوجيه:** قائمة origins بيضاء صريحة من متغيّر بيئة + `credentials: true` بعد الانتقال إلى الكوكيز.

### P0-5 🔴 Rate limiting وهمي على Cloudflare

**الملفات:** `src/middleware/rate-limit.ts:14` و`src/middleware/security.ts:12`

```ts
const rateLimitStore = new Map<string, { count: number; resetAt: number }>();
```

**التحليل:** يوجد **مخزنان منفصلان** لتحديد المعدل (تكرار)، وكلاهما `Map` في ذاكرة العملية. على Cloudflare Workers الذاكرة:
- غير مشتركة بين مواقع الحافة (300+ موقع).
- تُمحى مع إعادة تدوير الـisolate.

النتيجة: حد "10 محاولات دخول / 15 دقيقة" يمكن تجاوزه بمجرد تغيير موقع الاتصال أو انتظار تدوير الـisolate. **حماية الدخول من التخمين معدومة فعلياً.**

**التوجيه:** جدول `rate_limits` في D1 بمفتاح `(key, window_start)` + `Cloudflare WAF Rate Limiting` كطبقة أولى. احذف أحد المخزنين المكرّرين.

### P0-6 🔴 رمز الجلسة يسافر في عنوان URL

**الملفات:** `src/middleware/auth.ts:31`, `src/client/services/SseService.ts:57,96`

```ts
const sessionId = authHeader?.replace('Bearer ', '')
    || c.req.query('token')        // ← الرمز في الـURL
    || getCookie(c, 'sessionId');
```

**التحليل:** الرمز في query string يُسجَّل في: سجلات Cloudflare، سجل المتصفح، ترويسة `Referer`، وأي proxy وسيط. التعليق في الكود يبرّرها بأن `EventSource` لا يرسل ترويسات مخصصة — وهذا صحيح، لكن الحل خاطئ.

**التوجيه:** تذكرة اتصال قصيرة العمر (30–60 ثانية، استخدام واحد، مرتبطة بالمستخدم والقناة) تُستبدل بجلسة عند فتح الاتصال. أزل `?token=` من `authMiddleware` بعد ذلك.

### P0-7 🔴 الجلسة في `localStorage` — أي XSS = سرقة حساب

**الملفات:** `AuthService.ts:38,70,93,162,241,467`, `ApiClient.ts:31`, و**16 موضعاً** في `src/modules/pages/*`.

**التحليل:** ثلاث مشكلات متراكبة:
1. `localStorage` مقروء لأي سكربت — ومع CSP تسمح بـ`unsafe-inline` و`unsafe-eval` (`security.ts:130`) فسطح XSS واسع.
2. **تعدد مصادر الحقيقة**: `sessionId` في `localStorage` و`session_id` في صفحات الأدمن والمعلن — **مفتاحان مختلفان لنفس الشيء**. هذا خلل يسبب "خروج غامض" في لوحات معيّنة.
3. `window.sessionId` مكشوف عالمياً في `competition-page.ts`.

**التوجيه:** كوكي `HttpOnly; Secure; SameSite=Lax` يُصدره الخادم. تدوير معرّف الجلسة بعد الدخول. توحيد المفتاح الواحد. الخادم لا يعيد الرمز إلى JS إطلاقاً.

### P0-8 🔴 نقاط الخدمة محمية بترويسة `Origin` فقط

**الملف:** `src/modules/api/chunks/routes.ts:25,96,133`

```ts
const origin = c.req.header('Origin') || c.req.header('Referer') || '';
const isAllowed = allowedOrigins.some(a => origin.startsWith(a));
```

**التحليل:** `Origin`/`Referer` ترويستان يضبطهما العميل. أي `curl -H "Origin: https://allowed.com"` يمرّ. ونقطة `DELETE /:key` محمية بها — أي **حذف ملفات فيديو بلا مصادقة حقيقية**.

خلل إضافي: `origin.startsWith(allowed)` يعني أن `https://dueli.maelshpro.com.attacker.net` يمرّ إذا كان المسموح `https://dueli.maelshpro.com`.

**التوجيه:** توقيع HMAC خادم-لخادم بسرّ مشترك + `timestamp` + `nonce` لمنع الإعادة. وإن بقي فحص Origin، فمطابقة تامة لا `startsWith`.

### P0-9 🔴 سرّ الـcron في query string

**الملف:** `src/modules/api/cron/routes.ts:21`

```ts
const provided = c.req.query('key');
```

**التحليل:** `GET /api/cron/run?key=SECRET` — السرّ يُسجَّل في كل سجلات الطلبات. وهو مسار يشغّل **توزيع الأرباح** (`ScheduledTaskService`)، أي أن تسريبه يعني تشغيل المحرك المالي عند الطلب.

## 3. المخاطر البنيوية (P1)

### 3.1 انحراف معماري: 265 استعلام SQL خارج طبقة النماذج

`docs/01-ARCHITECTURE-RULES.md` يفرض: *"المنطق في `models/`، لا SQL في الصفحات"*. القياس الفعلي:

| الطبقة | عدد `.prepare()` | الحالة |
|---|---|---|
| `src/lib/` | 100 | ⚠️ خدمات تستعلم مباشرة |
| `src/modules/api/` | 81 | 🔴 انحراف |
| `src/controllers/` | 80 | 🔴 انحراف |
| `src/modules/pages/` | 4 | 🔴 خرق صريح للقاعدة |

**أكبر المخالفين:** `AdminController.ts` (34)، `CompetitionController.ts` (28)، `analytics/routes.ts` (24)، `users/delete-account.ts` (21).

**لماذا هذا خطر وليس مسألة ذوق:** `delete-account.ts` يحتوي 21 استعلاماً — أي أن حذف الحساب (التزام GDPR) منطق موزّع في ملف مسار. أي جدول جديد يُضاف لاحقاً سيُنسى هنا، فتبقى بيانات يتيمة. هذا خطر قانوني لا خطر جمالي.

**التوجيه:** لا إعادة كتابة شاملة. القاعدة: **أي ملف تلمسه لسبب آخر، تُخرج SQL منه**. ومنع الزيادة بحدّ أقصى في CI (`ratchet`).

### 3.2 خلل Durable Object: البث بعد الـhibernation

**الملف:** `workers/dueli-realtime/src/index.ts:28,107`

```ts
private readonly sockets = new Set<WebSocket>();   // حالة في الذاكرة
...
for (const ws of this.sockets) { ws.send(payload); }
```

الكود يستخدم `state.acceptWebSocket()` (السطر 65) — أي أنه **يفعّل Hibernation API**. لكن عند إيقاظ الكائن بعد hibernation تُبنى نسخة جديدة و`sockets` تكون **فارغة**، بينما الاتصالات ما زالت حيّة. النتيجة: البث يتوقف بصمت — لا خطأ، لا سجل، فقط لا شيء يصل.

**التوجيه:** `this.state.getWebSockets()` في كل بثّ. `sockets` تُحذف نهائياً. اختبار hibernation إلزامي.

### 3.3 SSE يستهلك D1 بشكل غير قابل للتوسّع

**الملف:** `src/modules/api/sse/routes.ts:113,123` — استعلام كل **2 ثانية** لكل اتصال.

الحساب: 1,000 مستخدم متصل = 30,000 استعلام/دقيقة = **43.2 مليون استعلام/يوم**. هذا يتجاوز حدود D1 ويجعل التكلفة غير محتملة قبل الوصول إلى أي حجم معقول.

**التوجيه:** WebSocket/DO هو المسار الأساسي (البنية موجودة أصلاً). SSE يبقى fallback بفترة استقصاء أطول (10 ثوان) وحدّ أقصى للاتصالات المتزامنة.

### 3.4 صفر اختبارات — الخطر الجامع

مقابل 43,762 سطراً و191 مساراً. النتيجة العملية: `PLAN-STATUS.md` يصنّف 20+ مهمة كـ"✅ مكتملة ومختبرة" بينما لا يوجد اختبار واحد يمنع رجوعها. **هذا ليس نقص تغطية، بل عدم قابلية للدفاع.**

الأولوية ليست تغطية 80% فوراً، بل تغطية **المسارات التي تفقد المال أو تسرّب البيانات**: التوزيع المالي، السحب، الصلاحيات، دورة المنافسة.

### 3.5 مصفوفة الصلاحيات غير مُحكَمة

من الجرد الآلي (`docs/14-ROUTE-INVENTORY.md`):

| التصنيف | العدد |
|---|---|
| بلا حاجز وسيط | 76 |
| `auth-optional` (الفحص داخل المعالج) | 77 |
| مصادقة مفروضة بالوسيط | 36 |
| خدمة بـOrigin فقط ⚠️ | 2 |

**قراءة معمارية دقيقة:** الـ76 ليست كلها ثغرات. مسارات مثل `payment-methods` تستدعي `this.requireAuth(c)` داخل المتحكّم، ولأن `c.get('user')` غير مضبوط (لا وسيط auth) فهي **تفشل مغلقة** — ترجع 401 دائماً. أي أنها **ميزات معطّلة**، لا أبواب مفتوحة. وهذا في ذاته عيب: ميزة الدفع لا تعمل ويُظن أنها تعمل.

لكن الاعتماد على "الفحص داخل المعالج" في 77 مساراً هو **نمط هشّ**: نسيان سطر واحد = ثغرة صامتة. الوسيط يفشل مغلقاً؛ الفحص اليدوي يفشل مفتوحاً.

**التوجيه:** كل راوتر يعلن سياسته صراحةً بالوسيط. المسار العام يُعلَن عاماً عن قصد، لا بالسكوت.

### 3.6 تناقض الوثائق مع الكود

- `docs/04-STREAMING-PIPELINE.md` مُشار إليه وغير موجود (`ls docs/` يؤكد).
- `README.md` يذكر `db:migrate` بينما `package.json` يعرّف `db:migrate:local` فقط.
- `db:reset` يستخدم **PowerShell** — يفشل على Linux/macOS وعلى CI.
- `AGENTS.md` يقول إن donations/payments "غير مربوطة" بينما `main.ts:139-141` يربطها.

الوثيقة التي تكذب أخطر من غياب الوثيقة، لأنها تُنتج قرارات خاطئة بثقة.

## 4. تصحيحات على التخطيط السابق

التخطيط الذي وصلني **جيد ودقيق في معظمه**، ومعظم بنوده تأكّدت بالفحص. لكن الأمانة الهندسية تقتضي تسجيل ثلاثة فروق:

| # | ما ورد سابقاً | التصحيح بعد الفحص |
|---|---|---|
| 1 | «ثغرة Hono 4.10.6 عالية الخطورة — رقّها فوراً» | الثغرة في **`hono/jwk` middleware** تحديداً. الفحص: `grep -rn "jwk\|jwt" src` → **صفر نتائج**. المشروع لا يستخدمها، فالخطر **غير قابل للاستغلال حالياً**. الترقية مطلوبة نظافةً لا طارئاً. **الأخطر فعلياً 12 ثغرة high في سلسلة البناء** (`vite`, `rollup`, `postcss`, `undici`, `sharp`) — وهي تهدد بيئة البناء لا الإنتاج. |
| 2 | «المصادقة موزّعة» (عام) | التشخيص أدق: **مفتاحان متنافسان** — `sessionId` في `AuthService` و`session_id` في `admin-dashboard-page.ts:168` و`advertiser-portal-page.ts`. هذا يفسّر أعراض "خروج غامض" في تلك اللوحات. |
| 3 | لم يُذكر | **P0-2: خلل محاسبي في `withdrawn`** + غياب ذرّية المعاملات + `on_hold` معرّف وغير مستخدم. أخطر بند مالي في المشروع، وكان غائباً عن التخطيط السابق. |

وإضافة: التخطيط السابق قدّر «198 مساراً»؛ الجرد الآلي يقول **191**. الفرق ليس مهماً بذاته، لكن **الرقم الآن مولَّد آلياً وقابل للتحقق** بدل التقدير.

## 5. الحكم المعماري والتوصية

### ما لا أوصي به

- ❌ **إعادة البناء.** النواة سليمة، وإعادة البناء تُهدر 43 ألف سطر عاملاً وتُعيد المخاطر نفسها.
- ❌ **أي ميزة جديدة قبل المرحلة 2.** (لا AI moderation، لا ميزات اجتماعية، لا توسّع في الإعلانات.)
- ❌ **تنظيف معماري شامل الآن.** نقل 265 استعلاماً دفعةً واحدة بلا اختبارات = إدخال أخطاء بلا شبكة أمان. النظافة تأتي **بعد** الاختبارات، لا قبلها.

### ما أوصي به

الترتيب الحاكم — وسببه أن كل خطوة تحمي التي تليها:

```
1. إيقاف نزيف المال والوصول   (P0-1, P0-2, P0-8, P0-9)  ← 2–3 أيام
2. شبكة أمان الاختبارات + CI  (المالية والصلاحيات أولاً)  ← 1–2 أسبوع
3. المصادقة والجلسات          (P0-4, P0-6, P0-7, P0-3)   ← 4–6 أيام
4. الوقت الحقيقي والبث        (3.2, 3.3)                  ← 1–2 أسبوع
5. صلابة دورة المنافسة        (E2E كامل)                   ← 2–3 أسابيع
6. النظافة المعمارية          (3.1) — انتهازياً، لا كحملة
7. الإدارة والسلامة، ثم UX/PWA/الأداء
```

**سبب تقديم الاختبارات على إصلاح الجلسات** (خلافاً للترتيب البديهي): نقل المصادقة إلى الكوكيز يلمس **113 مساراً** تعتمد المصادقة. بلا اختبارات، هذا التغيير يكسر المنصة بصمت. لكن P0-1 و P0-2 تُصلَح قبل كل شيء لأنها تفقد المال **الآن**، وإصلاحها موضعي ومحدود الأثر.

### التقدير

| الفريق | المدة إلى "جاهز للإنتاج" |
|---|---|
| مطوّر واحد | 9–13 أسبوعاً |
| 2–3 مطورين + QA | 5–7 أسابيع |

البث عبر شبكات حقيقية والتكامل المالي قد يضيفان وقتاً يعتمد على أطراف خارجية.

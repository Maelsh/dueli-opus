# 11 — تعريف «مكتمل» (Definition of Done)

> **هذه وثيقة حاكمة، لا إرشادية.** المهمة التي لا تجتاز البوابة تبقى `🔧 جارية` — ولو كانت الميزة تعمل على شاشة المطوّر.
>
> **سبب وجود هذه الوثيقة:** `PLAN-STATUS.md` يصنّف 20+ مهمة كـ«✅ مكتملة ومختبرة» بينما المشروع يحتوي **صفر اختبارات آلية**. كلمة «مختبرة» فقدت معناها. هذه الوثيقة تستعيده.

---

## 1. المبدأ الحاكم

> **«مكتمل» = يمكن لشخص آخر إثبات أنها تعمل، بأمر واحد، بعد سنة، دون سؤالك.**

الفحص اليدوي ليس اختباراً. الفحص اليدوي **حدث**؛ الاختبار **أصل**. الحدث يمضي، والأصل يحمي.

نتيجةً لذلك، ثلاث عبارات ممنوعة في `PLAN-STATUS.md` و`WORKLOG.md`:

| ممنوع | لماذا | البديل |
|---|---|---|
| «مختبرة ✅» بلا ملف اختبار | ادعاء غير قابل للتحقق | «مُتحقَّقة يدوياً 🔧» + رابط الاختبار المطلوب |
| «E2E حقيقي ✅» بلا سكربت | نفس السبب | اسم ملف Playwright |
| «تعمل عندي» | ليست معياراً هندسياً | مخرَج CI |

---

## 2. البوابة الإلزامية — 8 شروط

لا تُعلَن أي مهمة مكتملة قبل اجتياز **الثمانية كلها**.

### G1 — البناء ✅
```bash
npm run build
```
ينجح بصفر أخطاء. لا استثناء.

### G2 — الأنواع ✅
```bash
npx tsc --noEmit
```
صفر أخطاء. **ولا زيادة في عدد `any`:**
```bash
grep -rho ': any\|as any' src --include=*.ts | wc -l    # الأساس الحالي: 308
```
> قاعدة السقف المتحرّك (ratchet): الرقم يجوز أن ينزل، ويُمنع أن يرتفع.

### G3 — الاختبار الآلي ✅
المهمة تُرفق **باختبار قابل لإعادة التشغيل** يفشل قبل التغيير وينجح بعده.

| نوع المهمة | الاختبار الأدنى المطلوب |
|---|---|
| منطق مالي (أرباح، سحب، تبرع) | **Unit + Integration + اختبار عدم ذرّية** — إلزامي 100% |
| مصادقة أو صلاحية | Integration: يمرّ للمصرَّح، **و401/403 لغير المصرَّح** |
| مسار API جديد | Integration + تسجيل في `docs/14-ROUTE-INVENTORY.md` |
| تغيير مخطط DB | تطبيق الترحيل من **قاعدة فارغة** + اختبار سلامة مرجعية |
| دورة المنافسة | E2E Playwright بأدوار متعددة |
| واجهة | E2E للمسار السعيد + حالة الخطأ |

> **لا يُقبل** اختبار يتحقق من «عدم الانهيار» فقط. الاختبار يتحقق من **النتيجة**.

### G4 — المراجعة الأمنية ✅
قائمة فحص لكل تغيير يلمس مساراً أو بيانات:

- [ ] المسار مُعلَن صراحةً في مصفوفة الصلاحيات (لا حماية بالسكوت)
- [ ] الحماية **بالوسيط** لا بفحص داخل المعالج (الوسيط يفشل مغلقاً)
- [ ] المدخلات مُتحقَّقة (نوع، مدى، طول)
- [ ] لا SQL بسَلسَلة نصوص — `bind()` فقط
- [ ] لا سرّ في query string
- [ ] لا `Math.random()` في سياق أمني
- [ ] رسائل الخطأ لا تكشف تفاصيل داخلية للعميل
- [ ] الأفعال الحسّاسة تُسجَّل في `admin_audit_logs`
- [ ] `npm audit` لم يزد عدد ثغراته العالية

### G5 — سلامة قاعدة البيانات ✅
```bash
rm -rf .wrangler/state/v3/d1
npm run db:migrate:local && npm run db:seed
```
ينجح **من قاعدة فارغة**. وإن لمست المخطط:
- [ ] ترحيل **جديد** (`00XX_*.sql`) — لا تعديل على القديم
- [ ] `FOREIGN KEY` + `ON DELETE` صريح
- [ ] فهارس للأعمدة المستعلَمة
- [ ] `CHECK` للقيم المحدودة، ومنع السلبية في الحقول المالية

### G6 — الوثائق مطابقة للكود ✅
- [ ] `PLAN-STATUS.md` محدَّث بالحالة الصادقة
- [ ] `WORKLOG.md` يسجّل ما تغيّر ولماذا
- [ ] لا إشارة إلى ملف غير موجود
- [ ] لا أمر `npm` في التوثيق غير معرَّف في `package.json`
- [ ] نص ظاهر جديد ⇒ موجود في `i18n/ar.ts` **و**`en.ts`

### G7 — تحقّق على staging ✅
- [ ] يعمل على بيئة منفصلة عن الإنتاج
- [ ] المسار السعيد + **مسار الفشل** مُجرَّبان
- [ ] لا خطأ في سجلات الـWorker
- [ ] لا انحدار في المسارات المجاورة

### G8 — قابلية التراجع ✅
- [ ] التغيير قابل للتراجع بدفعة عكسية، **أو** خطة تراجع موثّقة
- [ ] ترحيل مدمّر ⇒ نسخة احتياطية قبله + إجراء استعادة مُجرَّب
- [ ] الميزات الكبيرة خلف مفتاح تشغيل (feature flag)

## 3. جدول الحالة المصحَّح

`PLAN-STATUS.md` يستخدم من الآن هذه الرموز:

| الرمز | المعنى | الشرط |
|---|---|---|
| `☐` | لم تبدأ | — |
| `🔧` | جارية | العمل قائم |
| `🧪` | **مُتحقَّقة يدوياً** | تعمل، **ولا اختبار آلي** ⇒ ليست مكتملة |
| `✅` | مكتملة | **اجتازت G1–G8** |
| `⛔` | معطّلة | يُذكر المانع صراحةً |

> **إجراء تصحيحي واجب:** كل `✅` حالية في `PLAN-STATUS.md` تخصّ منطقاً (لا توثيقاً) تُخفَّض إلى `🧪` حتى يُكتب اختبارها. هذا ليس تشكيكاً في العمل المنجَز — بل تسمية الحالة باسمها الصحيح.

## 4. بوابة خاصة: المسارات المالية

المال لا يُدار بمعايير الميزات العادية. أي تغيير يلمس `user_earnings` أو `withdrawal_requests` أو `donations` أو `platform_*_ledger` يجتاز **إضافةً** إلى G1–G8:

### M1 — الثابت المحاسبي (Invariant)
اختبار آلي يفرض بعد **كل** عملية:
```
total == available + pending + on_hold + withdrawn
```

### M2 — الذرّية
كل تحويل مالي في `db.batch([...])` واحد. **يُمنع** نمط «خطوتان + rollback يدوي في catch» — لأن موت الـWorker بينهما يفقد المال بصمت.

### M3 — منع السلبية
`CHECK (available >= 0 AND on_hold >= 0 AND withdrawn >= 0)` على المخطط، **و**اختبار يحاول تجاوزه ويتوقع الفشل.

### M4 — عدم التكرار (Idempotency)
كل webhook ومسار مالي يحمل مفتاح عدم تكرار مُخزَّناً. اختبار: **إعادة إرسال نفس الحدث مرتين ⇒ أثر مالي واحد.**

### M5 — أثر التدقيق
كل حركة مالية تكتب سجلاً غير قابل للتعديل يحمل: من، ماذا، متى، المبلغ، السبب، الحالة قبل وبعد.

### M6 — لا حالة مالية بلا سلطة
لا تتغيّر حالة دفع إلا من مزود الدفع عبر webhook موقَّع، أو من مشرف بسجل تدقيق. **لا مسار عام يغيّر حالة مالية إطلاقاً.**

## 6. الاستثناء الوحيد

يجوز دمج تغيير لا يجتاز البوابة في حالة واحدة: **إصلاح عاجل لثغرة إنتاجية نشطة.** وشروطه:

1. يُوسَم `hotfix` ويُذكر البند الذي تجاوزه.
2. تُفتح مهمة متابعة **في نفس الـPR** لسداد الدين.
3. تُسدَّد خلال **7 أيام** أو تُعلَن `⛔ معطلة`.

الدين التقني المعلَن مقبول. الدين الخفي هو ما قتل مصداقية `PLAN-STATUS.md`.

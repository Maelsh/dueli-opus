- **Root cause (proven).** `public/sw.js` — the file Cloudflare Pages actually serves for `/sw.js` (the worker's own `/sw.js` route is excluded from the worker by the generated routes config, so the static copy wins) — served `/static/*` **cache-first under a fixed cache name** while the asset URLs are unversioned (`/static/app.js`, `/static/styles.css`). A new deployment therefore kept serving the previous bundle, and an ordinary reload combined fresh HTML (new per-request CSP nonce) with stale JS/CSS. The violations were a *symptom* of the stale bundle, not of the current code.
- **Fix — and why a version bump is NOT it.** `/static/*` is now **network-first with a cache fallback**, so a deployed asset is always picked up by a normal navigation/reload and the cache survives purely as the offline fallback. This is version-independent: renaming the cache (v2 → v3, done as well for hygiene) would have been recreated by the next deployment, because nothing about a cache name changes when only built assets change. Also: install warms with `cache: 'reload'` (an install can never capture a stale copy), every successful response refreshes the cache, `activate` deletes every cache the running version does not own, and `skipWaiting()` + `clients.claim()` make a new worker take over immediately. `public/sw.js` and the worker-served `src/config/pwa.ts` were drifted copies; both now carry the same lifecycle and a test fails if they diverge. Not cached: cross-origin, `/api/*`, media/stream paths, range requests, non-200, and `no-store`.

Audit result: the codebase writes **no** style attribute at runtime; the only runtime writes are CSSOM (`style.cssText` / `setProperty`) and `data-csp-style`, neither of which `style-src` blocks — `SettingsUI` performs no style writes at all.
